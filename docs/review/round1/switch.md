## Verdict

The primary approval design is plausible, but the plan does not yet establish its advertised authorization guarantee.
The biggest problem is an unblocked Switch tool that lets a same-owner helper widen pi-desk's addressing policy.
Second, the proposed steward tries to change its own addressing, which current source explicitly refuses, and omits essential reconnect behavior.
Third, the Windows, session-count, document-display and follow-up assumptions do not describe one reproducible runtime configuration.
The template vocabulary is substantially correct; inventing replacement field names would make this plan worse.
Score: **5.0/10**, using approval boundary 1/4, provider/runtime truth 1.5/2, template correctness 1.5/2, and reproducibility 1/2.

## Verified facts

- **A project MCP tool can plausibly produce a native Switch card through this adapter.** Both inspected adapter versions pass the agent working directory, permit project MCP configuration, and register `canUseTool`. Current SDK defaults load filesystem settings when `settingSources` is omitted. This is source-backed feasibility, not a completed S2. Sources: [release adapter][release-adapter], [SDK defaults][sdk].
- **Ask rules take precedence over allow rules in current Claude documentation.** Consequently a correctly loaded matching ask rule should beat a session allow. Session approval does not inevitably bypass ask rules. Source: [Claude permissions][permissions]. Installed-version proof remains SW-04's gate.
- **The adapter really rescopes session approval suggestions to session storage.** It does not itself create a request-specific scientific authorization record. Its mocked tests assert the returned permission-update structure. Sources: [adapter][adapter], [tests][adapter-tests].
- **Card answers check addressing permission.** `answer_approval` checks authority, request state and expiry; a refused answer leaves the request unsettled. Platform presses also check the card token's channel/post match. Sources: [approval service][approval-service], [bridge answers][bridge-answers].
- **Agent text is excluded from the typed-answer path.** `for_text` rejects app senders. The current answerer type is a platform person or signed-in Switch user, not an agent. This supports E2E-12. It does not prevent a helper changing another agent's policy as in SW-01. Sources: [bridge answers][bridge-answers], [approval service][approval-service].
- **Native card answers can be given from Console/web as well as the chat bridge.** The claim that everyone must have a messaging claim to answer anything is too broad; the stricter claim is that the claimed PI platform identity must satisfy the gate's owner policy. Source: [approval service][approval-service].
- **The settled Mattermost attribution exists.** Upstream settled-card tests assert the chosen actor and platform. That attribution establishes a platform decision record, not a laboratory signature or compliance certification. Source: [settled-card tests][settled-tests].
- **All questioned template field families are real:** aliases, roles, docs, auto_mode, auto_approve, typed agent/user inputs, group/rooms/links, provider/location/directory, and both correct kickoff placements. No unsupported-field correction was found for the supplied room/parameter blocks. Sources: [template language][templates], [room/parameter models][rooms-yaml], [Console agent parser][template-parser].
- **Aliases can use interpolated mapping keys and directory strings can contain parameters.** Executing upstream `interpolate` on both checked-in YAML files produced the expected `rao-*` alias keys and all five `C:/Dev/LabQuorum/agents/...` directories. The static comparison found 0 unknown parameter fields and 0 unknown room fields in either file. This was not a live import or full provisioner validation. Source: [interpolation implementation][rooms-yaml].
- **Optional user parameters are supported.** An omitted optional entity reference drops out of a list, so the two optional member slots need not be replaced with invented sentinel values. Source: [parameter resolution][rooms-yaml].
- **Template addressing and operation addressing use different valid values.** `owner` and `owner-agents` are template shortcuts; `owner_only` and `owner_and_owner_agents` are operation values. `anyone` is shared. Source: [template mapping][template-runs].
- **The global one-live-role constraint is real in inspected main.** A role belongs to a room, but acquiring a new role checks the agent's existing live lease across rooms. Keeping project templates free of roles is a sensible simplification. Source: [role store][roles].
- **Room documents have a creating-agent update restriction; context does not automatically cross rooms.** Static template documents and dynamic agent-created documents should retain their distinct ownership paths. Sources: [context docs][context], [document operations][ops].
- **WebSocket plus HTTP is the current custom-agent transport.** Registration and agent keys are distinct; duplicate registration returns conflict and overwrite rotates the key. The trusted event sender is opaque; enrollment must compare the whole ID. Sources: [protocol][protocol], [event identity][events].
- **The fallback's durable inbox plus mutation transaction supports duplicate rejection.** Its testable invariant is one effect per accepted message despite replay; this does not make receipts and chat commits atomic. Sources: [connection][connection], `docs/inputs/gpt-6.1-sol/plan.md` minimal protocol client.
- **Console v0.40.1 was still the latest release returned by GitHub during this review**, published 2026-10-21. Issue #1335 was open and unresolved at fetch time. Sources: [release][release], [issue][issue1335].
- **Windows `.cmd` launching is explicitly handled by the Claude adapter.** No custom shell wrapper needs to be invented for that case. Source: [release adapter][release-adapter].
- **The server media default is 20 MiB.** This is separate from the lower host intake limit. Source: [server config][config].
- **The named commands exist**, including `!agents-status`, `!roles`, `!list-documents`, targeted `!interrupt`, `!compact`, and `!reset`. Reset/interrupt/compact require an explicit target unless using their separately named all-agent forms; their availability is provider-dependent. Source: [room commands][commands].
